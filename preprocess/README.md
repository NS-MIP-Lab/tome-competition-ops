# 前処理 — XDF と課題データを学習用の表にする

`task_data/` に溜まった記録を、そのままモデルに渡せる表へ一括変換します。

```bash
pip install -r lsl/requirements.txt        # pyxdf が必要（pylsl には依存しません）
python preprocess/build_dataset.py
```

引数で窓の作り方を変えられます。

```bash
python preprocess/build_dataset.py --window 10 --hop 2 --horizon 20
python preprocess/build_dataset.py --no-gaze-samples      # 視線の生データを書かない
python preprocess/build_dataset.py --task-data task_data --out dataset
```

---

## 出力

既定では `dataset/` に出ます。**設定を変えて作り直すことがあるので、窓の作り方が分かる名前を付けてください。**

```
dataset_win10_hop1_horizon10/    --window 10 --hop 1 --horizon 10（既定値）
```

```bash
python preprocess/build_dataset.py --out dataset_win10_hop1_horizon10
```

`dataset/` と `dataset_*/` は `.gitignore` 済みです（再生成できるので追跡しません）。すべて `utf-8-sig`、列名は日本語です。

| ファイル | 1行の意味 |
|---|---|
| `coverage.csv` | セッション × ストリーム。**最初にこれを見てください** |
| `surface_fit.csv` | 座標変換の当てはまり採点（4通り） |
| `gaze_regions.csv` | 視線1サンプル。領域・ブロック・設問つき |
| `features_step.csv` | 被験者 × 問題 × 設問 |
| `features_window.csv` | 被験者 × 問題 × 窓 |
| `train_window.csv` | **そのまま学習に渡せる形にした窓単位の表** |
| `train_columns.csv` | `train_window.csv` の列の役割 |

モデルに渡すのは `train_window.csv` の1つだけです。`coverage.csv` と `surface_fit.csv` は人が目視するための表で、欠けや当てはまりを確かめてから使うセッションを決めます。

### `coverage.csv` を先に見る理由

セッションごとに欠け方が大きく違います。**欠けたまま黙って学習に流すのが一番危ないので、件数を必ず表に出します。**

`判定` 列でそのセッションが使えるかが分かります。

| 判定 | 意味 |
|---|---|
| `使用可` | 特徴量を作った |
| `中断` | 途中で止めた回。XDF の末尾が欠け、課題データも保存されていない |
| `課題データなし` | XDF はあるが `events.csv` が無い |
| `視線なし` | サーフェスが一度も検出されなかった |
| `整列不可（task_startなし）` | 時刻の原点が無く、他のデータと突き合わせられない |
| `XDFなし` | 課題データだけがある |

**`中断` は異常ではありません。** 記録を途中で止めた回はこうなります。特徴量は作らずに飛ばします。

`注記` 列には、切り落としたバイト数やファイルの対応づけの失敗が入ります。

## 学習用の表（`train_window.csv`）

`features_window.csv` は「判断材料を全部載せる」表なので、文字列の列が混ざり、値は絶対値のままで、課題の進行度も入っています。**そのままモデルには渡せません。** それを整えたのが `train_window.csv` です（[train_table.py](train_table.py)）。元の表は書き換えません。

### 列の役割

`train_columns.csv` に一覧が出ます。

| 役割 | 列 | 使い方 |
|---|---|---|
| 識別子 | `被験者ID` `問題ID` | 特徴量ではない。**`被験者ID` を `GroupKFold` の `groups` に渡す** |
| 注記 | `標準化の基準` | どの区間で正規化したか |
| ラベル | `介入要請あり` `介入要請までの秒数` `理解度正誤` `自己評価理解度` | |
| マスク | `介入ラベル有効` `理解度ラベル有効` `自己評価ラベル有効` `脳波有効` | 損失に掛けるか、入力に足す |
| 特徴量 | 残り | |

**落とす列** … `アルゴリズム` `条件`（問題IDとセッションで決まるので冗長）、`脳波_品質`（`脳波有効` に落としてある）、`窓終了秒` `窓長秒`（窓開始秒と窓長から決まる）。

**`理解度正誤`** は 正解=1 / 不正解=0 / 空欄=NaN に直します。

### 正規化

**`log1p` を掛けてから、被験者ごとに平均と標準偏差で z 化します。**

帯域パワー（µV²）や件数は右に強く裾を引くので、そのまま正規化すると値が発散します。S03/pE を最初の3分で正規化したときの `|z|` の最大は次のとおりでした。

| 方式 | p99 | 最大 |
|---|---|---|
| そのまま平均/標準偏差 | 12.58 | 489.7 |
| 中央値/MAD | 23.96 | 718.3 |
| **log1p → 平均/標準偏差** | **9.46** | **64.4** |

中央値/MAD は、MAD が0になる列（`脳波_サンプル数` など基準区間でほぼ一定）が列ごと NaN になるため使いません。`log1p` は負の値を含まない列だけに掛けます（`脳波_前頭左右差α` は対数比なので対象外）。

**既定は課題の最初の3分を基準にします**（`--standardize baseline --baseline-min 3`）。実運用でも同じことができる形にするためです。セッション全体を使う `session` は未来のデータを使うので、交差検証は通っても実運用の形ではありません。

**交差検証との関係。** 正規化は被験者ごとに閉じており、`GroupKFold` も被験者ごとに分けるので、分割をまたいだ漏れは起きません。テスト被験者の値はその被験者自身の統計で正規化されます。

基準区間で値が動かない列は、セッション全体の広がりで割り、実行時に注記を出します。

### 引数

```bash
--standardize {baseline,session,none}    既定 baseline
--baseline-min 3.0                       基準にする区間（分）
--eeg-columns {relative,absolute,both}   既定 relative（相対パワーと総パワー）
--progress-columns                       進行度も特徴量に入れる
--no-train-table                         この2ファイルを書かない
```

**進行度（`設問` `窓開始秒`）は既定で外しています。** 押下は課題の終盤と特定の設問に偏るため、入れるとモデルが生体情報を見ずに「終盤なら押される」と学習できてしまいます。S03/pE では押下6回のうち2回が最後の5%に入っていました。入れる場合は `設問` を one-hot にします。

### 標本数に注意

**窓は9秒ぶん重なっています。** 押下1回から作られる正例は10行ですが、中身はほぼ同じです。S03/pE は正例60行 / 全4789行でしたが、独立した事象は押下6回です。

本実験9セッション（被験者4名）の押下は**合計20回**です。行数で数えず、押下回数で数えてください。**分割は必ず `被験者ID` で。**

## 時刻の合わせ方

XDF の中は LSL のローカル時計、課題ページは「開始ボタンからの経過ミリ秒」。この2つをつなぐのは `ExperimentMarkers` の **`task_start` ただ1点**です。

```
XDF時刻 = task_start の LSL時刻 + 経過秒
```

読み込んだ時点で全ストリームを経過秒へ直すので、以降の処理は LSL 時計を意識しません。記録開始は課題開始より前なので、`経過秒` は負の値から始まります。

**`task_end` には頼りません。** 実際の記録では入っていませんでした。課題の終端は `events.csv` のセッション行の `終了経過ミリ秒` を使います。

**途中で切れた XDF も読みます。** 記録を途中で止めると末尾のチャンクが欠け、`pyxdf` が `struct.error` で落ちます。最後の完全なチャンク境界まで切り落として読み直し、`注記` に残します。切り落とされるのは数十バイトなので、データの損失は実質ありません。

## 視線の座標系

`layout.csv` はウィンドウ座標（左上原点）、Pupil のサーフェス座標は左下原点です。向きが違うので変換します。

```
x_window = x_surface        （左右はそのまま）
y_window = 1 - y_surface    （上下は反転）
```

**この向きは実データで確かめたものです。** 視線 x の分布が二山になり、細い山（0.10〜0.25、全体の14%）が `layout.csv` のコード文字範囲（0.02〜0.22）と重なり、幅広い山（0.55〜0.95、86%）が設計書側（0.50〜1.00）と重なりました。y はコードの x 帯に絞って検証し、文字範囲に入る割合が反転あり 52.8% / 反転なし 32.3% でした。

**縦のずれと伸びは残っています。** タグはベゼルに貼るためサーフェスは画面より広く、実測の山は該当ブロックの範囲より広く散ります。そのため変換は決め打ちにせず、`Transform` の係数（`scale_y` / `offset_y`）で調整できる形にしてあります。セッションごとの当てはまりは `surface_fit.csv` の `文字範囲一致率_コード帯` で確認してください。**この値が 50% を大きく下回るセッションは、ブロック別の特徴量を信用しないでください。**

### 何を見ていたか

| 視線の位置 | 割り当て |
|---|---|
| コード領域（`x < 0.5`） | ブロックID `B1`〜`B6` |
| 設計書領域（`x >= 0.5`） | その時刻に表示していた設問 `Q1`〜`Q6` |
| サーフェス外 | `画面外` |

設問は1度に1つしか出ないので、設計書側の「大問」は設問滞在イベントから一意に決まります。

`サーフェス内` 列は Pupil の `on_surface` フラグ、`領域` 列はこちらの判定結果です。フラグが立っていても座標が範囲外の点があるため、両者はわずかにずれます。

## ラベル（マルチタスク学習向け）

**主のタスクは介入要請のタイミング**です。ヒントボタンが押されると `support` マーカーが入ります。補助タスクとして理解度テストの正誤と自己評価を同じ表に載せてあります。

| 列 | 種類 | 粒度 |
|---|---|---|
| `介入要請あり` | 二値 | 窓（終わりから `horizon` 秒以内に `support` があれば 1） |
| `介入要請までの秒数` | 回帰 | 窓（次の `support` まで。無ければ空欄） |
| `介入要請回数` | 計数 | 設問 |
| `理解度正誤` | 二値 | 設問（正解 / 不正解） |
| `自己評価理解度` | 順序 1〜5 | **セッション**（Q6 の5段階） |

### 損失マスク

行ごとに「どのラベルが使えるか」を持っています。マルチタスクの損失を掛けるときはこれで外してください。

| 列 | 0 になる条件 |
|---|---|
| `介入ラベル有効` | 条件が検証用のとき |
| `理解度ラベル有効` | Q6（理解度テストが無い）、理解度テスト表示中の窓、設問の外の窓 |
| `自己評価ラベル有効` | Q6 が未記入のとき |

**検証用のセッションには介入要請の教師信号が原理的に存在しません。** ヒントボタンは学習用にしか出ないためです。データの約半分が主タスクの正解を持たない構成になるので、マスクは必須です。

**介入要請の正例が0件のときは、実行の最後に警告を出します。**

### 粒度のずれに注意

ラベルの粒度が3段階でばらけています。

| タスク | 1セッションあたりの実際の標本数 |
|---|---|
| 介入要請 | ヒントを押した**回数**（窓の数ではない） |
| 理解度テストの正誤 | 5問 |
| 自己評価理解度 | 1個 |

**窓は 80% 重なっています。** 1回の押下から作られる窓（5秒・1秒ずらし・10秒先読みなら10行）はほぼ同じデータなので、標本数として数えないでください。同じ理由で、**`自己評価理解度` は同じ値が数百行に複製されます。** 損失に重みを掛けるか、セッション単位のヘッドを分けてください。

**分割は被験者ごとに。** 窓が重なっているので、無作為分割だと同じ瞬間が訓練とテストの両方に入り、性能が実際より高く出ます。`被験者ID` で `GroupKFold` を使ってください。

### 設計書の記述内容は使いません

`answers.csv` に入っている記述回答（被験者が書いた詳細設計書そのもの。pA で51欄）は、**ラベルにも特徴量にも使いません。** 自由記述なので人が模範解答と突き合わせないと正誤が付かず、そのコストに見合わないと判断しました。理解度の教師信号は選択式の理解度テスト（`理解度正誤`）だけを使います。

**ただし `answers.csv` は読み続けます。** JSON が無いセッションで理解度テストの正誤を拾うフォールバックに使っているためです（[task_io.py](task_io.py) の `quizzes()`）。

## 特徴量

区間の切り出し方だけを変えて、設問単位と窓単位で同じ関数を使います。**値が取れないときは NaN を返し、行は落としません。** 落とすかどうかは学習側で決めてください。

### 脳波（Muse 4ch / 256 Hz）

1〜40 Hz の帯域通過（Butterworth 4次、ゼロ位相）→ Welch。帯域内を積分した値（µV²）です。

サンプリング周波数は公称 256 Hz で固定しています。**本実験9セッションで実測したところ、実効レートは 256.0299〜256.0303 Hz、サンプルの取りこぼしは0件でした。** 実効レートを `fs` に入れてはいけません（muselsl がタイムスタンプを公称値の格子に載せるため循環します）。詳細は [features.py](features.py) の `EEG_RATE` のコメントにあります。

`θ` 4〜8、`α` 8〜13、`β` 13〜30、`低γ` 30〜40 Hz。加えて `脳波_θα比` と `脳波_前頭左右差α`（AF7 と AF8 の α の対数比）。

#### `低γ` を皮質γ活動として扱わないこと

**乾式電極の 30〜40 Hz に出るのは主に筋電です**（側頭筋・前頭筋・首）。列は残しますが、**論文で「γ帯の脳活動」として書かないでください。** 「筋緊張を含む高周波帯」が正確です。

列を消さないのは、筋電そのものが目的に対して有用だからです。顎を噛みしめる・顔がこわばるといった緊張は認知負荷や行き詰まりと関係するので、介入タイミングの推定には拾いたい信号です。

**筋電か皮質活動かは確認できます。** 筋電なら4chが同時に上がり、`脳波_振幅超過率` と相関します。皮質活動なら部位差が出ます。`dataset/` を作り直したらチャネル間の相関を見てください。

`脳波_振幅超過率` は 200 µV を超えたサンプルの割合で、1割を超えると `脳波_品質` が `振幅過大` になります。**TP9・TP10 は耳電極でノイズが大きく、前頭より1桁高い値が出ます。** チャネル間で直接比べないでください。

#### 品質のマスク

`脳波_品質` を 0/1 に落とした `脳波有効` を持ちます。ラベル側の `〇〇ラベル有効` と同じ使い方です。**行は落としません。**

| `脳波_品質` | `脳波有効` |
|---|---|
| `有効` | 1 |
| `振幅過大`（振幅超過率 > 10%） | 0 |
| `区間が短い`（64サンプル未満） | 0 |
| `データなし` | 0 |

**窓単位は 0/1 ですが、設問単位は 0〜1 の小数になります。** 訪問ごとの値を滞在時間で重み付けして平均するため、「その設問の滞在時間のうち脳波が有効だった割合」になります。設問単位で使うときは閾値を決めてください。

10% という閾値は S01/pA の実測（p99 が 72〜162 µV、瞬目で 800 µV 超）から置いたもので、**本実験9セッションでの分布は未確認です。** `dataset/` を作り直したら `脳波有効` が 0 の行がどれくらいあるか確かめてください。多すぎる／少なすぎる場合は `EEG_ARTIFACT_UV` と閾値を見直します。

**µV² の絶対値は被験者をまたいで比べられません。** 電極の当たり・髪・インピーダンスで数倍変わります。瞳孔と同じく、**学習側でセッションごとに標準化してください。** 被験者ごとに分割する構成（`GroupKFold`）では、標準化しない絶対パワーはテスト被験者でスケールが合わず効きません。

#### 相対パワー

`脳波_{ch}_{帯域}相対` は、その帯域をチャネルの4帯域合計で割った比です。**窓ごとに比を取るので、その窓の共通ゲインが割り落ちます。** 首に力が入る・電極がずれるといった原因で全帯域が同時に上下する成分は、列ごとの標準化では消えません。

分母は4帯域の合計（≒4〜40 Hz）です。**1〜40 Hz の積分にしません。** 4 Hz 未満には瞬目のエネルギーが乗るため、分母に入れると相対パワーが瞬目に振られます。合計が 1 になるので4列のうち1列は冗長です（木系のモデルなら害はありません）。

比にすると振幅そのものが消えるので、`脳波_{ch}_総パワー`（4帯域の合計、µV²）を別列で残します。こちらは絶対値なので、標準化が必要な列です。

**まずは相対パワーと総パワーだけで回して、絶対パワーと比べてください。** 両方を同時に渡すと、どちらが効いたのか分かりません。

### 心拍（Garmin Venu 3S）

`hr_bpm` と `rr_ms` の JSON から、平均HR・RMSSD・SDNN・pNN50。RR は 300〜2000 ms の外を捨てます。`rr_ms` は数値でもリストでも受けます（実データは数値でした）。

**5秒窓では RR が数拍しか入りません。** RMSSD や pNN50 を使うなら `--window` を伸ばしてください。

### 瞳孔

**`diameter_2d`（px）を主に使います。** `diameter_3d`（mm）は1回目の記録で約半分が NaN で、値が出ているときも eye0 が 1.36、eye1 が 2.17 と左右で60%食い違いました。3D 眼球モデルが校正されていないと判断しています。`瞳孔_3d有効率` で状況を確認できます。

**px は絶対値に意味がありません。** 目とカメラの距離で変わるので、学習側でセッションごとに標準化してください。

### 注視

`fixation_id` でまとめて数えます。**`注視_平均時間ms` は1回目の記録では 307〜308 ms でほぼ一定でした。** Pupil 側の検出設定によるものと見られ、この記録では情報になりません。`注視_回数` を使ってください。

### 視線

領域とブロックの割合、コードと設計書の `往復回数`。割合の分母は画面内にあったサンプルで、画面外の割合は `視線_画面内率` で別に持ちます。

**ブロック列は `B1`〜`B6` の固定です。** 問題によってブロック数が違うため（pA は5個、pC と pD は6個）、無いブロックの列は 0 になります。コード側のサンプルが1つも無い窓では NaN です。

## 設問単位の作り方

設問は行き戻りがあるため、1つの設問に複数の訪問区間が対応します。訪問ごとに特徴量を出し、滞在時間で重み付けして1行にまとめます。件数と回数の列だけは合計します。

`滞在ミリ秒` と `訪問回数` は、課題ページの JSON の `設問別合計` と一致することを確認済みです。

## ファイルの対応づけ

XDF は `/start` の時刻、JSON 以下は `/save` の時刻で名前が付くため、**時刻印は一致しません。** JSON の中の `XDFファイル` の**ファイル名部分**で照合します（中身は記録した機械の絶対パスなので、パスは使いません）。

見つからない場合は、同じフォルダに XDF が1つだけならそれを使い、`注記` に残します。

## モジュール

| ファイル | 役割 |
|---|---|
| `build_dataset.py` | CLI と一括処理の入口 |
| `xdf_io.py` | XDF 読み込み、`task_start` 基準への整列、破損した末尾の切り落とし |
| `task_io.py` | `events.csv` / `layout.csv` / `answers.csv` / JSON の読み込みと対応づけ |
| `regions.py` | 座標変換、領域とブロックの判定、当てはまり採点 |
| `features.py` | 脳波・心拍・瞳孔・視線の特徴量 |
| `train_table.py` | `features_window.csv` を学習に渡せる形へ整える |

`lsl/view_xdf.py` の `stream_name()` / `channel_labels()` を使い回しています。同じ読み方を二重に持たないためです。
